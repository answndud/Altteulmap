## 근거 규칙

- 코드 위치는 가능한 경우 파일과 함수 또는 route를 함께 적는다.
- 수치가 없는 성능 문서는 결과가 아니라 측정 계획으로 표시한다.
- 실행하지 않은 provider OAuth, 실제 트래픽, 백업 복구, secret 교체는 미검증이다.
- 기존 영문 문서는 삭제하지 않고 원문·결정 기록으로 보존한다. 이 디렉터리의 한국어 문서는 설명과 링크의 canonical 진입점이다.

## 이번 리뷰에서 보완한 문제

기존 문서 세트는 폴더와 주제는 넓었지만 다음 문제가 있었다.

1. “공개 제보 → AI 검수 → 관리자 승인”이 실제로는 어디서 분리되는지 route와 함수까지 추적되지 않았다.
2. 가격 제보 insert와 관리자 승인 transaction을 같은 정합성 단계처럼 설명했다.
3. API 전체 목록, access boundary, validation, rate limit, DB write, test 근거가 한눈에 연결되지 않았다.
4. 성능 문서가 p95 숫자와 측정 방법을 구분했지만 iterations, warmup, percentile 방식과 결과 해석 제한이 부족했다.
5. AI suggestion schema/panel과 외부 AI provider 생성 pipeline을 충분히 구분하지 않아 README·resume에 과장 가능성이 있었다.
6. 운영 문서가 절차를 적었지만 실제 실행, 명령 존재 확인, 미검증 rehearsal의 차이를 더 강하게 표시할 필요가 있었다.

이번 보완에서는 API 계약 지도, 가격 제보 호출 추적, 제품·기술 수용 기준, 위협 모델 잔여 위험, 성능 결과 해석 규칙, 면접 심화 질문을 추가했다. README와 resume의 AI 관련 표현도 현재 코드가 증명하는 범위로 낮췄다.

## source of truth 우선순위

문서가 충돌하면 다음 순서로 판단한다.

1. 실행 중인 route·repository·schema 코드
2. migration과 실제 검증 테스트/스크립트
3. wrangler/package/CI 설정
4. canonical 한국어 문서
5. 기존 PRD/TRD와 resume/blog 문서

기존 문서의 문장은 코드나 실행 결과를 인용하지 않으면 목표·가설로 취급한다.
