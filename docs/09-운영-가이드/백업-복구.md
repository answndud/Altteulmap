# 백업·복구

## 운영 원칙

- 운영 DB 백업은 공급자 기능(Supabase PITR/자동 백업)을 1차로 사용하고, 애플리케이션 저장소에는 비밀값을 저장하지 않는다.
- 복구 대상은 production과 분리된 disposable/staging PostgreSQL이어야 한다. source와 restore URL이 같은 DB이면 도구가 즉시 중단한다.
- seed, `db:push`, 임의의 destructive SQL은 복구 리허설에 사용하지 않는다.
- 복구 증적에는 연결 비밀번호, access token, 사용자 이메일 본문을 기록하지 않는다.

## 리허설 명령

`pg_dump`와 `pg_restore`가 설치된 승인된 운영 작업 환경에서 다음을 실행한다.

```bash
BACKUP_SOURCE_DATABASE_URL="$PRODUCTION_DATABASE_URL" \
BACKUP_RESTORE_DATABASE_URL="$STAGING_RESTORE_DATABASE_URL" \
BACKUP_REHEARSAL_CONFIRM=I_UNDERSTAND_RESTORE_REHEARSAL \
BACKUP_ARTIFACT_DIR="artifacts/backup-rehearsal-$(date +%Y%m%d-%H%M%S)" \
npm run db:rehearse:backup
```

도구는 source snapshot을 읽고 custom-format backup을 생성한 다음 restore DB에 `pg_restore --clean --if-exists --exit-on-error`로 복구한다. 복구 후 핵심 테이블 row count와 가격 무결성 invariant를 비교한다.

## 증적과 판정

- `evidence.json`의 `result`가 `passed`이고 source/restore 식별자, 생성 시각, backup byte 수, SHA-256, table snapshot이 있어야 한다.
- RPO는 backup 시각과 장애 시각의 차이로 기록한다. RTO는 복구 시작부터 read-only health·핵심 조회 검증 완료까지 측정한다.
- row count 불일치, invalid price, restore 오류, checksum 불일치는 실패로 판정하며 production 배포 승인을 중단한다.
- 백업 artifact는 승인된 암호화 저장소에만 보존하고, 작업 종료 후 로컬 작업 디렉터리에서는 삭제한다.

## 현재 상태

저장소에는 안전한 복구 리허설 명령과 판정 규칙이 있다. 실제 production 공급자 backup/PITR과 별도 restore DB 실행은 운영 권한과 승인된 staging 자격 증명이 필요하며, `evidence.json`이 생성되기 전에는 복구 완료로 보고하지 않는다.
