# 장애 대응

## 1차 분류

1. /api/health 응답과 status를 확인한다.
2. DB deep health와 migration 상태를 확인한다.
3. Cloudflare Worker 배포 output과 binding/secret 존재 여부를 확인한다.
4. public read가 503인지, validation/권한 오류인지 구분한다.
5. 마지막 배포와 migration 순서를 비교한다.

## 증상별 힌트

| 증상 | 우선 확인 |
| --- | --- |
| 모든 API 503 | DATABASE_URL/Hyperdrive, DB availability, timeout |
| 지도만 느림 | bbox 크기, result cap, query plan, map measure |
| public write 실패 | Turnstile secret, body cap, visitor rate limit, migration |
| admin 403 | session expiry, role, cookie origin |
| OAuth callback 실패 | redirect URI, state cookie, client secret, provider response |

## telemetry와 알림 판정

Worker 요청 완료 로그는 `worker_request_complete` JSONL event로 `requestId`, method, path, status, durationMs를 남긴다. 처리되지 않은 예외는 `worker_unhandled_error`, 방문 telemetry 저장 실패는 `worker_telemetry_write_failed` event로 구분한다. 이 event에는 token, password, cookie, request body를 기록하지 않는다.

수집된 JSONL 로그는 다음 명령으로 임계치를 검사한다.

```bash
npm run ops:check-alerts -- ./worker-logs.jsonl --max-p95-ms=1000 --max-5xx=5 --max-429=50 --max-oauth-failures=5
```

기본 임계치는 단일 수집 구간 기준 p95 1초 초과, 5xx 5건 초과, 429 50건 초과, OAuth callback 오류 5건 초과다. 결과가 `alert`이면 배포·반복 mutation을 중단하고 `requestId`로 원본 로그를 조회한다. 실제 Cloudflare Logpush/Sentry/알림 채널의 수집과 threshold 연결은 운영 계정에서 별도 설정하고, 이 parser 결과를 해당 알림의 동일 기준으로 사용한다.

실제 장애 주입과 복구 rehearsal은 운영 권한으로 수행한다. 원인 확정 전 production mutation을 반복하지 않는다.
