# 제품 요구사항: 현재 상태

## 목적과 사용자

알뜰맵은 주변의 저렴한 식당·생활 서비스 정보를 지도와 가격 이력으로 탐색하게 하는 웹 서비스다. 핵심 사용자는 대학생, 자취생, 사회초년생, 점심 수요자처럼 생활비를 줄이려는 사람이다. 비회원 탐색을 허용해 진입 장벽을 낮추고, 회원에게는 북마크를 제공한다.

## 핵심 여정

1. 사용자가 홈 또는 지도에서 지역·카테고리를 선택한다.
2. 클라이언트가 viewport 기준 장소 목록을 조회한다.
3. 장소 카드에서 대표 가격과 검증 상태를 보고 상세 페이지로 이동한다.
4. 상세에서 가격 항목, 이력, 댓글, 신고 기능을 사용한다.
5. 회원은 북마크하고, 비회원 또는 회원은 장소·가격·댓글·신고를 제출한다.
6. 운영자는 admin 큐에서 장소·가격·신고·moderation suggestion을 검토하고 공개 상태를 결정한다.

## 현재 포함 범위

- 공개 지도/목록/상세 조회와 카테고리·가격 필터
- 장소 등록, 가격 제보, 댓글, 신고
- 가격 제보의 중복 식별과 검증 상태 계산
- 회원 credentials 로그인, Kakao/Naver OAuth route, signed session
- 회원 북마크와 방문·공유 활동 집계
- 관리자 장소·가격·신고·moderation suggestion 조회 및 mutation
- 공공데이터 provenance 필드와 import metadata

## 상태 전이

| 대상 | 상태 또는 조건 | 다음 상태 |
| --- | --- | --- |
| 장소 | pending | admin 승인 또는 반려 |
| 가격 제보 | 제출 | 승인/반려 후 검증 집계 대상 |
| 가격 항목 | 동일 이름·금액 승인 제보가 2건 이상 | verified |
| 신고 | open | admin 처리 상태로 변경 |
| moderation suggestion | pending | applied 또는 superseded |
| 세션 | 유효 signed cookie | 만료·로그아웃 시 무효화 |

코드의 정확한 허용 상태는 src/db/schema.ts, src/db/schema-moderation.ts, src/worker/admin의 validation 파일을 기준으로 한다.

## 권한 차이

| 역할 | 가능 범위 |
| --- | --- |
| Public | 장소 목록·상세·카테고리·health의 공개 부분 조회 |
| Guest write | visitor actor와 Turnstile/rate limit을 통과한 장소·가격·댓글·신고 |
| Authenticated | 로그인, 북마크, 본인이 만든 actor 콘텐츠의 허용된 삭제 |
| Admin | admin route 조회와 장소·가격·신고·moderation mutation |
| Provider callback | OAuth state와 provider 응답을 검증한 callback |

## 오류와 예외

- 잘못된 JSON·query·path는 Zod/route validation 실패로 거부한다.
- 세션·role이 없으면 인증/관리자 API는 거부한다.
- DB timeout은 mock 데이터로 조용히 대체하지 않고 오류 응답으로 드러낸다.
- public write는 body 크기, Turnstile, visitor/IP rate limit을 함께 적용한다.
- 지도 bbox가 비정상이거나 결과가 상한을 넘으면 제한된 조회 결과를 사용한다.

## 의도적으로 제외하거나 미완료인 범위

- 실제 외부 AI provider가 자동으로 검수하는 pipeline은 현재 코드의 완료 기능으로 기록하지 않는다. 현재는 moderation suggestion 데이터와 admin 적용 경계가 핵심이다.
- 장소 merge mutation은 운영자 UX와 rollback 정책이 정해진 뒤의 backlog다.
- 실제 provider OAuth 계정 연동 sandbox, 백업 복구, 공개 트래픽 부하, secret 교체는 실행 근거가 없다.
- 네이티브 모바일 앱, 자동 가격 수집, 추천 엔진, 광고 플랫폼은 MVP 밖이다.

## 완료 조건

기능 완료는 UI가 존재하는 것만으로 판단하지 않는다. route validation, 권한, DB 상태 전이, 실패 응답, unit/E2E 근거가 함께 있어야 한다. 현재 검증된 명령과 미검증 범위는 [테스트 워크플로](../04-실행-가이드/테스트-워크플로.md)와 [기능 대조표](../05-기능-대조/대조표.md)를 따른다.

## 제품 요구사항의 검증 가능한 형태

| 사용자 가치 | 최소 완료 조건 | 현재 증거 | 아직 모르는 것 |
| --- | --- | --- | --- |
| 주변 장소를 찾음 | bbox/category/query로 목록과 지도가 같은 데이터 집합을 사용 | places-read route/repository, map E2E | 실제 검색 성공률 |
| 가격을 믿고 비교함 | pending 제보가 admin 승인 후에만 대표 가격/검증 상태에 반영 | admin-price-review transaction, price-review E2E | 허위 제보율·가격 최신성 |
| 쉽게 참여함 | guest도 장소/가격/댓글/신고를 제출하고 actor/rate limit로 제한 | public-write routes, unit/E2E | anonymous conversion과 abuse 비용 |
| 다시 방문함 | 회원 bookmark와 visit/share activity를 저장·조회 | bookmarks/telemetry routes | retention/cohort |
| 운영 가능함 | admin queue, audit action, migration/deploy guard | admin routes, scripts, CI | 실제 1인 운영 처리량 |

이 표에서 “현재 증거”는 구현·자동 검증의 근거이고, “아직 모르는 것”은 제품 analytics나 production 실험 없이는 결론낼 수 없는 가설이다.
