# 기술 노트

## signed session

일반적인 의미 → 서버가 검증 가능한 cookie payload로 로그인 상태를 유지하는 방식이다.

이 프로젝트에서 사용한 이유 → Worker에서 별도 session store를 줄이고 credentials/OAuth를 같은 경계로 묶기 위해서다.

실제 위치 → src/worker/auth/session.ts, src/worker/routes/auth-session.ts.

실행 흐름 → 로그인 성공 → signed cookie 발급 → request에서 검증 → role/user 확인 → signout/만료 처리.

흔한 오해 → 서명은 암호화가 아니며 visitor가 실명 사용자라는 뜻도 아니다.

trade-off → 단순하지만 secret rotation, replay와 cookie 정책을 운영해야 한다.

꼬리질문 → key rotation을 어떻게 무중단으로 할 것인가?

## transaction과 조건부 update

일반적인 의미 → 여러 DB 변경을 하나의 원자적 단위로 묶고, 기대 version/status가 맞을 때만 update한다.

이 프로젝트에서 사용한 이유 → 가격 검증·admin stale mutation·report 상태 변경의 lost update를 줄이기 위해서다.

실제 위치 → price/report/admin repository와 schema/migration.

실행 흐름 → route validation → transaction → 조건부 update/insert → commit → UI revalidation.

흔한 오해 → transaction이 모든 중복 제출과 외부 재시도를 자동 제거하지는 않는다.

trade-off → 정합성은 좋아지지만 lock/timeout과 retry 정책이 필요하다.

꼬리질문 → 어떤 unique key와 isolation을 선택했는가?

## viewport query와 index

일반적인 의미 → 현재 화면 영역에 필요한 데이터만 조회하고 predicate에 맞는 index를 사용한다.

이 프로젝트에서 사용한 이유 → 전국 데이터 전체 로딩과 지도 응답 폭증을 피하기 위해서다.

실제 위치 → places-read-map-repository.ts, drizzle migration, scripts/measure-map-api.mjs.

실행 흐름 → bbox parse → coordinate range validation → category/query filter → cap → response.

흔한 오해 → p95 한 번이 모든 사용자 latency를 보장하지 않는다.

trade-off → cap은 안전하지만 넓은 화면에서 완전한 결과를 숨길 수 있다.

꼬리질문 → PostGIS와 단순 latitude/longitude 조건을 언제 바꿀 것인가?

## AI suggestion boundary

일반적인 의미 → 모델의 제안을 사람이 적용하기 전에 별도 상태와 schema로 다루는 구조다.

이 프로젝트에서 사용한 이유 → 자동 공개와 운영자의 최종 판단을 분리하기 위해서다.

실제 위치 → src/db/schema-moderation.ts, src/worker/admin/moderation-suggestion-validation.ts.

실행 흐름 → suggestion 저장/조회 → schema·stale 상태 검증 → admin 적용.

흔한 오해 → schema가 있다고 외부 모델 pipeline이나 AI 정확성이 검증된 것은 아니다.

trade-off → 안전한 인간 승인 경계지만 provider 비용·queue·retry는 아직 없다.

꼬리질문 → prompt injection과 개인정보를 어떻게 처리할 것인가?
