# 기술 질문 은행

### 프로젝트 구조와 핵심 trade-off는?

30초 답변: Vite React SPA와 Hono Worker BFF, PostgreSQL을 단일 배포 경계로 묶어 1인 운영 복잡도를 낮췄습니다.

2분 답변: 브라우저는 DB를 모르고 Worker route가 validation·auth·actor를 거친 뒤 repository를 호출합니다. 단순성 대신 SSR, queue, cache를 포기했으므로 timeout·result cap·migration guard를 안전장치로 뒀습니다.

심화 설명: [아키텍처 개요](../02-설계/아키텍처-개요.md)와 src/worker/index.ts.

예상 꼬리질문: 트래픽이 늘면 무엇부터 분리할 것인가?

프로젝트 근거 파일: src/client, src/worker, src/db.

검증 명령 또는 테스트: npm run verify, npm run cf:build:vite, npm run deploy:check:vite.

답변할 때 주의할 과장·오해: Hyperdrive와 microservice를 이미 운영한다고 말하지 않는다.

### transaction은 어디서 시작·종료되는가?

30초 답변: HTTP route가 입력과 권한을 확인하고 repository가 transaction을 열어 가격·admin 상태 변경을 원자적으로 처리합니다.

2분 답변: unique/check와 조건부 update가 애플리케이션 계산의 빈틈을 보완하며, commit 뒤에만 성공 응답과 UI 갱신을 허용합니다.

심화 설명: [주요 도메인 설계](../02-설계/주요-도메인-설계.md)의 장소와 가격 절.

예상 꼬리질문: 두 요청이 동시에 같은 가격을 제출하면?

프로젝트 근거 파일: src/worker/places-write-price-reports-repository.ts, src/worker/admin/admin-price-items-repository.ts, src/db/schema-pricing.ts, drizzle migrations.

검증 명령 또는 테스트: npm run smoke:price-concurrency.

답변할 때 주의할 과장·오해: 모든 race를 제거했다고 말하지 말고 검증한 시나리오를 한정한다.

### 인증과 ownership은 어떻게 다른가?

30초 답변: 인증은 session user를 확인하는 것이고 ownership은 해당 user 또는 visitor actor가 대상 리소스와 연결되는지 확인하는 것입니다.

2분 답변: admin은 role을 별도로 확인하고, 익명 댓글 삭제는 signed visitor actor와 대상의 owner를 비교합니다. cookie 기반 actor는 강한 신원 인증이 아닙니다.

심화 설명: [보안 가이드](../07-보안/보안-가이드.md).

예상 꼬리질문: cookie를 재발급하면 rate limit을 우회하지 않는가?

프로젝트 근거 파일: src/worker/public-write-actor.ts, src/worker/auth/session.ts, src/worker/routes/public-write-comments.ts.

검증 명령 또는 테스트: npm run test:unit, login/signup/comments E2E.

답변할 때 주의할 과장·오해: 실제 공개 abuse 검증을 완료했다고 말하지 않는다.

### 성능 결과는 어떻게 측정했는가?

30초 답변: map:measure의 고정 시나리오와 브라우저 E2E를 분리하고, fixture·환경·날짜를 함께 기록했습니다.

2분 답변: historical map p95는 서울 viewport 37ms, food 36ms, global query 224ms였지만 1k seed 전후 특정 환경이며 production SLO가 아닙니다. p50/p99와 resource metric이 없는 항목은 미기록으로 남겼습니다.

심화 설명: [성능 안내](../06-성능/안내.md).

예상 꼬리질문: 언제 Hyperdrive를 도입하는가?

프로젝트 근거 파일: scripts/measure-map-api.mjs, src/worker/db.ts, wrangler.jsonc.

검증 명령 또는 테스트: npm run map:measure.

답변할 때 주의할 과장·오해: 개선률이나 전체 사용자 latency를 임의로 계산하지 않는다.

### 장애가 나면 어느 계층부터 보는가?

30초 답변: health와 Worker response를 먼저 보고, DB timeout/connection, migration 상태, provider/asset 경계를 순서대로 좁힙니다.

2분 답변: DB unavailable은 mock으로 숨기지 않으므로 503과 health를 확인하고, deploy output·migration contract·Cloudflare binding을 점검합니다. 이후 read-only smoke로 공개 경로를 확인합니다.

심화 설명: [장애 대응](../09-운영-가이드/장애-대응.md).

예상 꼬리질문: rollback과 migration rollback은 어떻게 다른가?

프로젝트 근거 파일: src/worker/routes/health.ts, scripts/check-production-db.mjs, scripts/migrate-production.mjs.

검증 명령 또는 테스트: npm run db:check:production, npm run smoke:remote.

답변할 때 주의할 과장·오해: 실제 장애 복구 rehearsal을 했다고 말하지 않는다.

### 왜 PostgreSQL 직접 연결을 유지하고 Hyperdrive를 보류했는가?

30초 답변: 현재 데이터 규모와 측정 결과에서는 direct connection이 충분했고, Hyperdrive는 connection/latency evidence가 생길 때 도입하도록 조건을 남겼습니다.

2분 답변: src/worker/db.ts는 Hyperdrive connectionString을 우선하지만 DATABASE_URL로 fallback합니다. wrangler binding은 아직 없으며, map p95·DB timeout·connection churn을 trigger로 정의했습니다. 먼저 도입하면 binding·local dev·rollback 복잡도가 늘어나므로 측정 가능한 문제를 기준으로 미뤘습니다.

심화 설명: [성능 개선 회고](../06-성능/개선-회고.md), [Cloudflare 결정 기록](../project/hyperdrive-decision-2026-05-08.md).

예상 꼬리질문: connection limit이 실제로 포화되면 어떤 변경 순서인가?

프로젝트 근거 파일: src/worker/db.ts, wrangler.jsonc, docs/deploy/deploy-cloudflare.md.

검증 명령 또는 테스트: npm run map:measure, npm run smoke:remote.

답변할 때 주의할 과장·오해: Hyperdrive를 이미 사용 중이라고 말하지 않는다.

### 공개 제보와 관리자 승인을 왜 분리했는가?

30초 답변: 공개 제보는 낮은 진입 장벽을 위해 pending 데이터로 받고, 공개 반영과 검증 상태 확정은 admin transaction에서 수행합니다.

2분 답변: public route는 actor·rate limit·Turnstile을 거친 뒤 price_reports에 pending_review를 저장합니다. admin 승인 transaction은 accepted count, distinct reporter identity, price_items, snapshot, place summary, admin_actions를 함께 갱신합니다. 따라서 악의적 입력이 바로 대표 가격이 되지 않습니다.

심화 설명: [주요 도메인 설계](../02-설계/주요-도메인-설계.md)의 장소와 가격 절.

예상 꼬리질문: 같은 사람이 cookie를 바꿔 두 번 제보하면?

프로젝트 근거 파일: src/worker/routes/public-write-price-reports.ts, src/worker/admin/admin-price-review-repository.ts, src/worker/price-report-identity.ts.

검증 명령 또는 테스트: npm run test:unit, npm run smoke:price-concurrency.

답변할 때 주의할 과장·오해: visitor actor가 실명·불변 신원이라고 말하지 않는다.

### API 계약과 frontend 타입 불일치를 어떻게 줄였는가?

30초 답변: route schema가 요청 경계에서 Zod로 검증되고, client query/mutation은 Worker JSON 응답 shape를 기준으로 사용합니다.

2분 답변: 서버는 malformed body를 저장하지 않고 status/message/error를 반환합니다. UI는 loading, empty, error를 분리하며 API 변경 시 route·repository·unit/E2E를 함께 확인합니다. 다만 별도 OpenAPI 생성이나 end-to-end 타입 자동 생성은 사용하지 않습니다.

심화 설명: src/features/places/write-schema.ts, src/worker/routes, tests/unit/http-and-rate-limit.test.ts.

예상 꼬리질문: schema를 client와 공유하지 않는 이유와 다음 개선은?

프로젝트 근거 파일: src/features/places/write-schema.ts, src/client, src/worker/routes.

검증 명령 또는 테스트: npm run typecheck, npm run test:unit.

답변할 때 주의할 과장·오해: compile-time에서 API 계약 전체가 자동 보장된다고 말하지 않는다.

### 테스트 계층을 왜 이렇게 나눴는가?

30초 답변: 순수 보안·validation 계약은 빠른 unit으로, 실제 route/page와 DB 상호작용은 E2E·smoke로 분리했습니다.

2분 답변: unit은 secret fail-closed, OAuth malformed state, Turnstile, actor, rate limit, moderation output처럼 경계 조건을 빠르게 회귀시킵니다. E2E는 로그인·가격 검수·댓글·admin·모바일·axe를 확인하고, concurrency smoke는 별도 disposable DB 흐름을 확인합니다.

심화 설명: [테스트 워크플로](../04-실행-가이드/테스트-워크플로.md).

예상 꼬리질문: 무엇이 아직 테스트되지 않았는가?

프로젝트 근거 파일: tests/unit/http-and-rate-limit.test.ts, tests/e2e, scripts/smoke-price-report-concurrency.ts.

검증 명령 또는 테스트: npm run verify, npm run test:e2e:all.

답변할 때 주의할 과장·오해: full E2E 통과를 실제 provider·공개 트래픽 검증으로 바꾸어 말하지 않는다.

### 장애와 rollback을 어떻게 분리해 판단하는가?

30초 답변: health/DB/runtime 장애와 잘못 배포된 code/schema를 먼저 구분하고, code rollback이 data rollback을 자동으로 의미하지 않는다는 전제로 접근합니다.

2분 답변: /api/health, migration history, DB timeout, last deploy를 확인한 뒤 read-only smoke를 수행합니다. migration이 이미 적용됐으면 이전 Worker만 재배포해도 schema가 되돌아가지 않으므로 backward compatibility와 별도 data recovery가 필요합니다.

심화 설명: [장애 대응](../09-운영-가이드/장애-대응.md), [롤백](../09-운영-가이드/롤백.md).

예상 꼬리질문: backup restore를 실제로 해봤는가?

프로젝트 근거 파일: scripts/check-production-db.mjs, scripts/migrate-production.mjs, docs/09-운영-가이드/백업-복구.md.

검증 명령 또는 테스트: npm run db:check:production, npm run smoke:remote.

답변할 때 주의할 과장·오해: 절차 문서를 실제 장애 경험으로 포장하지 않는다.
