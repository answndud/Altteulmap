# 기능 아이디어

현재 코드·데이터와 직접 연결되는 후보만 기록한다. 제품 실험이므로 구현 완료로 해석하지 않는다.

## 1. 가격 최신성 배지

- 해결할 문제: 대표 가격이 언제 확인됐는지 알기 어렵다.
- 근거: price_reports의 시각·provenance와 detail API.
- MVP 범위: 최근 확인일, 오래된 가격 경고, 사용자 재확인 CTA.
- 주요 변경: freshness 계산과 카드/detail 표시.
- 위험: 오래된 데이터를 과도하게 숨기면 검색 성공률이 낮아진다.
- 난이도: 중간. 기대 효과: 최신 제보 전환율 상승. 성공 지표: 재확인 제보율, 오래된 가격의 클릭률. 우선순위: A.

## 2. 지역별 빈 곳 제보 큐

- 해결할 문제: 데이터 밀도가 지역마다 다르다.
- 근거: viewport 조회, category와 admin 집계.
- MVP 범위: 검색 결과가 없는 지역의 필요한 카테고리와 간단 제보 CTA.
- 주요 변경: 지역 bucket 집계, abuse rate limit, 운영 큐.
- 위험: 빈 곳을 노출해 개인정보나 실제 수요를 추정할 수 있다.
- 난이도: 중간. 기대 효과: 지역별 데이터 밀도와 제보 전환율. 성공 지표: 빈 viewport 제보 시작률·승인률. 우선순위: B.

## 3. 제보 신뢰 요약

- 해결할 문제: 검증됨만으로는 왜 믿을 수 있는지 설명이 부족하다.
- 근거: 승인 제보 수, visitor/user actor, admin action, provenance.
- MVP 범위: 제보 수·최근 확인·공공데이터 여부를 설명형 UI로 표시.
- 주요 변경: 집계 API와 개인정보 비식별화.
- 위험: 숫자를 평점처럼 오해하거나 조작할 수 있다.
- 난이도: 중간. 기대 효과: 허위·중복 제보 감소. 성공 지표: 신고율·중복 승인율. 우선순위: B.

## 4. 중복 후보 운영 도우미

- 해결할 문제: duplicate analysis 결과를 수동으로만 확인한다.
- 근거: scripts/analyze-place-duplicates.mjs와 admin places/merge backlog.
- MVP 범위: 후보 pair 비교, dry-run, 원본 보존 확인 후 단건 merge.
- 주요 변경: admin UI, audit log, rollback 모델.
- 위험: 잘못된 merge가 가격·댓글·북마크를 잃게 할 수 있다.
- 난이도: 높음. 기대 효과: 운영 검수 비용 감소. 성공 지표: 후보 처리 시간·merge 후 복구 건수. 우선순위: A.

## 5. 공유 링크의 가격 시점 요약

- 해결할 문제: 공유받은 사용자가 링크만 보고 최신성 판단을 못 한다.
- 근거: visit_activity의 share source와 place detail route.
- MVP 범위: 공유 URL에 장소명·대표 가격·확인일을 표시하고 재방문을 집계.
- 주요 변경: OG/공유 payload, 개인정보·cache header 검토.
- 위험: stale cache가 가격을 오래 노출할 수 있다.
- 난이도: 낮음. 기대 효과: 재방문과 공유. 성공 지표: share 유입 후 detail 체류·북마크율. 우선순위: B.

## 6. 운영자 검수 묶음 처리의 안전한 초안

- 해결할 문제: 신고·가격·장소 큐를 하나씩 처리하면 1인 운영 비용이 크다.
- 근거: admin queues, admin_actions, CAS/status validation.
- MVP 범위: 같은 상태와 같은 유형의 preview-only batch, 실제 적용은 승인 후 단건 transaction.
- 주요 변경: batch preview, idempotency key, audit, partial failure report.
- 위험: 대량 오처리와 신고 폭탄이 장애로 이어질 수 있다.
- 난이도: 높음. 기대 효과: 검수 시간 감소. 성공 지표: 건당 처리 시간·rollback 없는 적용률. 우선순위: C.
