# 아키텍처 개요

## 전체 흐름

브라우저 React UI
→ Vite asset과 React Router
→ Hono Worker route
→ Zod validation
→ session 또는 visitor actor 확인
→ Turnstile/rate limit
→ repository/domain mutation
→ Drizzle/postgres
→ PostgreSQL
→ JSON response
→ UI query 갱신

공개 읽기와 공개 쓰기 모두 이 경계를 통과한다. 관리자 화면도 동일 Worker의 /admin UI와 /api/admin 서버 권한 검사를 사용한다.

## 요청 유형

| 유형 | 시작점 | 서버 경계 | 저장 여부 |
| --- | --- | --- | --- |
| 지도 읽기 | MapRoute | bbox/category/query validation, read repository | 없음 |
| 장소 상세 | PlaceDetailRoute | id validation, 공개 상태 filter | 없음 |
| 회원 로그인 | LoginRoute | credentials 또는 OAuth state/callback | users, auth_accounts, session cookie |
| 공개 제보 | SubmitRoute | body cap, Zod, actor, Turnstile, rate limit | places/price_reports/comments |
| 북마크 | BookmarksRoute | signed session + user ownership | bookmarks |
| 관리자 검수 | admin routes | session role 재검증 + CAS/transaction | places/prices/reports/admin_actions |

## 실제 호출 추적 예시: 가격 제보

가격 제보는 “POST route가 DB에 저장한다”로 끝나지 않는다.

1. src/worker/index.ts의 /api middleware가 POST body를 최대 256 KiB까지 읽고 초과 시 413을 반환한다.
2. src/worker/routes/public-write-price-reports.ts의 registerPublicWritePriceReportRoutes가 path id, JSON body, placePriceReportSchema를 읽는다.
3. getSessionFromRequest와 getWorkerPublicWriteActor가 user 또는 visitor actor를 결정한다.
4. consumePublicWriteRateLimit가 placePriceSubmission key와 actor를 기준으로 제한한다.
5. verifyTurnstileForPublicWrite가 production write token을 검증한다. local/mock bypass는 별도 조건에서만 허용된다.
6. DB 모드에서는 createDatabasePlacePriceReport가 장소를 확인하고 normalizePriceLabel과 getPriceReportSubmissionKey로 identity를 만든다.
7. src/worker/places-write-price-reports-repository.ts는 price_reports에 pending_review를 insert하고 submissionKey unique conflict를 멱등적으로 처리한다.
8. 이 단계에서는 가격을 검증됨으로 확정하지 않는다. PATCH /api/admin/prices/:id가 src/worker/admin/admin-price-review-repository.ts의 transaction 안에서 승인·반려, accepted count, price_items, snapshot, place summary, admin_actions를 갱신한다.
9. response는 no-store와 actor/rate-limit header를 포함하고, 성공적인 non-GET mutation 뒤에는 map preview cache를 무효화한다.

따라서 public write와 admin moderation을 하나의 “저장” 단계로 설명하면 실제 신뢰 경계를 놓치게 된다.

## 데이터 소유권

Worker만 DB 연결 정보를 가진다. route는 HTTP 계약과 권한을 소유하고 repository는 query/transaction을 소유한다. 가격 제보자는 user id 또는 visitor id로 추적하고, 공개 화면에는 필요한 상태와 provenance만 노출한다. 운영자 최종 판단은 moderation suggestion과 별도 mutation으로 구분한다.

## 실패 경계

validation 실패는 4xx, 인증/권한 실패는 401/403, 이미 처리된 가격 제보는 현재 route 구현상 404 계열로 응답하며, DB unavailable은 503으로 드러낸다. Hono 전역 onError는 requestId를 기록한 500 JSON을 반환한다. 정확한 status/body는 각 route와 tests/unit/http-and-rate-limit.test.ts를 기준으로 한다. 일반적인 “conflict 계열” 표현보다 실제 route의 status를 우선한다.

## 현재의 trade-off

단일 Worker와 단일 PostgreSQL은 1인 운영과 일관된 권한 경계에 유리하다. 반면 connection pool, queue, cache가 없으므로 공개 트래픽과 장시간 AI 작업을 직접 수용하는 구조는 아니다. 지도 결과 상한과 timeout은 이 단순성을 보호하는 안전장치다.
