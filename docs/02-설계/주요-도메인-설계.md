# 주요 도메인 설계

## 장소와 가격

문제와 책임: 장소를 공개 지도에서 탐색하고, 여러 가격 제보를 누적해 최신성과 검증 상태를 보여준다.

→ 데이터 모델: places, price_items, price_reports와 provenance/source 필드. schema와 migration의 unique/check/index가 기본 invariant를 보완한다.

→ 상태 전이: 장소는 운영자 승인 상태를 거치고, 가격 제보는 pending_review에서 admin approve/reject로 전이된다. 승인된 데이터만 검증 집계에 포함된다. 동일 장소·normalizedLabel·금액 조합에 대해 서로 다른 reporter identity가 2명 이상이면 verified로 계산한다. 같은 actor의 중복 제보는 submissionKey unique로 막지만, 검증 count의 distinct identity 정책은 moderation transaction에서 다시 적용된다.

→ application/service 경계: public-write-price-reports route가 validation/actor를 처리하고 places-write-price-reports-repository가 pending report를 멱등 insert한다. admin-prices route와 admin-price-review-repository가 운영자 mutation과 검증 계산을 담당한다.

→ 권한 규칙: public submit은 guest도 가능하지만 Turnstile/rate limit/actor가 필요하다. admin 변경은 서버 role 검증을 통과해야 한다.

→ transaction·동시성: 공개 제보 insert는 onConflictDoNothing(submissionKey)로 멱등 처리하고, admin 승인/반려와 price item·history·summary·audit 갱신은 moderateWorkerPriceReport의 transaction에서 처리한다. 조건부 update가 이미 처리된 pending report의 재처리를 막는다. local price concurrency smoke가 같은 actor의 중복 흐름을 제한하는지 확인했다.

→ 실패 응답: invalid input, actor/rate-limit failure, missing place, stale version, DB unavailable을 구분한다.

→ 테스트 근거: tests/unit/http-and-rate-limit.test.ts, tests/e2e/price-review.spec.ts, scripts/smoke-price-report-concurrency.ts. 서로 다른 actor가 동시에 같은 가격을 승인하는 부하 실험은 별도 범위다.

→ trade-off와 한계: append-only 이력은 감사 가능성이 높지만 정정·merge 정책이 필요하다. 장소 merge mutation은 아직 운영 UX와 rollback 조건을 확정하지 않았다.

## 인증과 visitor actor

문제와 책임: 회원 session과 익명 제출자를 구분하면서, 익명 쓰기의 남용을 제한한다.

→ 데이터 모델: users, auth_accounts, signed cookie, visitor actor 및 public_write_rate_limits.

→ 상태 전이: credentials/OAuth 성공 시 session 발급, signout/만료 시 삭제·무효화. OAuth state는 발급·검증·소비된다.

→ application/service 경계: auth routes와 auth/session helper가 session을 만들고, public-write-actor가 write identity를 결정한다.

→ 권한 규칙: admin은 role을 서버에서 재확인하며, comment 삭제는 작성자 actor 또는 admin만 허용한다.

→ transaction·동시성: rate-limit 기록과 콘텐츠 mutation의 일관성을 route/repository 단위에서 확인한다. visitor cookie 재발급만으로 강한 실명성은 보장하지 않는다.

→ 실패 응답: malformed state, token/profile failure, missing secret, unauthenticated/admin mismatch를 fail closed한다.

→ 테스트 근거: tests/unit/http-and-rate-limit.test.ts와 auth route 관련 테스트, tests/e2e/login.spec.ts, signup.spec.ts.

→ trade-off와 한계: 자체 signed session은 의존성이 적지만 key rotation과 provider sandbox 검증을 운영 절차로 추가해야 한다.

## moderation과 운영 판단

문제와 책임: 자동 제안이 있더라도 공개 데이터의 최종 판단은 운영자에게 남긴다.

→ 데이터 모델: moderation_suggestions의 status, modelVersion, promptVersion, inputFingerprint, confidence, summary.

→ 상태 전이: pending에서 운영자 적용 또는 superseded로 전이한다. schema의 기본 provider 값은 local_rule_agent지만, 현재 저장소에서 새 suggestion row를 생성하는 외부 provider 실행 경로는 확인되지 않는다. 따라서 seed/fixture 또는 별도 운영 입력으로 존재하는 suggestion을 조회·검증·표시하는 경계로 문서화한다.

→ application/service 경계: admin moderation route와 moderation-suggestion-validation이 입력과 stale 상태를 검사한다.

→ 권한 규칙: suggestion 적용은 admin 서버 권한을 요구하고, AI 제안 자체가 공개 상태를 확정하지 않는다.

→ transaction·동시성: 처리 완료된 대상에 stale suggestion이 적용되지 않도록 status/fingerprint와 조건부 mutation을 확인한다.

→ 실패 응답: malformed output, stale suggestion, 권한 실패를 거부한다.

→ 테스트 근거: tests/unit/http-and-rate-limit.test.ts의 moderation contract 테스트와 tests/e2e/submission-admin.spec.ts, price-review.spec.ts의 패널 흐름. suggestion 생성 정확도·모델 품질 테스트는 존재하지 않는다.

→ trade-off와 한계: 제안 schema는 운영 확장을 준비하지만 실제 모델 비용·timeout·retry·prompt injection 방어는 provider 연결 전까지 운영 검증 대상이 아니다.
