# 2026-11-24 k6 부하 측정과 개선

지연 측정([한국 측정](2026-11-24-한국-측정.md))은 요청 하나의 시간이었다. 여기서는 부하를 걸어 처리량과 병목을 찾고, 하나를 고친 뒤 같은 조건으로 다시 쟀다.

## 환경과 방법

| 구분 | 내용 |
| --- | --- |
| 로컬 | 맥 한 대에서 k6 · 빌드한 Worker(`wrangler dev`, workerd) · Docker Postgres 17이 함께 돈다. 장소 1,001곳. 네트워크 지연이 없어 **절대 수치가 아니라 전/후 비교용**이다 |
| 운영 | 한국 머신에서 k6가 운영 URL에 **읽기만** 보낸다. 운영 DB 쓰기는 하지 않는다 |
| staging | 쓰기·로그인은 운영과 **같은 경로**(한국 → Cloudflare → Hyperdrive → VPS)의 별도 Worker(`altteulmap-staging`)로 잰다. VPS의 같은 Postgres 컨테이너 안에 **분리된 DB**(`altteulmap_staging`)와 DML 전용 role을 만들고, 장소·가격 데이터만 복원했다(사용자·세션은 복사하지 않음). Turnstile은 Cloudflare 공개 테스트 키라 siteverify 외부 호출은 운영과 똑같이 한다 |
| 부하 모델 | 도착률(`ramping-arrival-rate`)로 초당 요청 수를 직접 지정한다. 처음에 쓴 닫힌 VU 루프는 서버가 느려지면 실패 응답에도 쉬지 않고 초당 수천 건을 몰아 스스로 서버를 무너뜨려(`connection refused`) 처리량 곡선을 못 얻었다 |
| 로컬 구성 | 지도 z11·z15와 장소 상세(모든 캐시 우회, `refresh=1`) 각 30%, 가격 제보 쓰기 10%. 쓰기는 요청마다 새 visitor·새 IP로 보내 rate limit이 아니라 쓰기 경로 자체를 잰다 |
| 재현 | `npm run perf:k6:local`(정점 `PEAK_RPS`, 기본 80), `npm run perf:k6:prod` |

## 1. 발견: 요청 하나가 연결을 여러 번 연다

요청 하나가 실제로 보내는 SQL 구문과 DB 연결 수를 Postgres 로그에서 세었다.

| 요청 | 변경 전 | 변경 후 |
| --- | --- | --- |
| 장소 상세 | 구문 2 · 연결 1 | 구문 1 · 연결 1 |
| 지도 z11 | 구문 2 · 연결 1 | 구문 1 · 연결 1 |
| 가격 제보(쓰기) | **구문 8 · 연결 3** | 구문 4 · 연결 1 |

- 서비스 6곳이 호출마다 `withWorkerDatabaseConnection`으로 새 연결을 열었고, 라우트의 rate limit·세션 조회도 각자 열었다. 가격 제보 하나가 연결 3개를 쓴 것이다.
- postgres.js는 새 연결마다 타입 조회 쿼리(`fetch_types`)를 한 번 더 보낸다. 가격 제보에서 3번 나왔다.
- 방문자 버킷과 IP 버킷 upsert가 따로 두 구문이었다.

운영에서는 연결 수립과 쿼리 왕복이 각각 약 0.2~0.4초라 구문·연결 수가 곧 지연이다([한국 측정](2026-11-24-한국-측정.md) §1).

## 2. 변경

| 변경 | 내용 |
| --- | --- |
| 요청당 연결 1개 | `/api/*` 미들웨어가 요청마다 연결 범위를 열고(연결은 첫 쿼리 때 지연 생성), 서비스·세션·rate limit은 `withExistingOrNewWorkerDatabaseConnection`으로 그 범위를 재사용한다 |
| 타입 조회 제거 | `fetch_types: false`. 이 앱은 DB 배열 타입을 쓰지 않는다(`inArray`는 개별 파라미터로 풀린다) |
| 버킷 한 문장화 | 방문자·IP(·추가 키) 버킷을 다중 행 `INSERT ... ON CONFLICT`로 한 번에 올리고 `actorKey`로 결과를 맞춘다 |
| 백그라운드 갱신 | SWR 갱신은 요청이 끝난 뒤에도 돌기 때문에 요청의 연결 범위를 쓰지 않고 자기 범위를 연다 |

주의: 연결은 `max: 1`이라, 트랜잭션 콜백 안에서 같은 범위의 비트랜잭션 쿼리를 중첩 호출하면 교착될 수 있다. 서비스는 트랜잭션 밖에서 호출되고, 통합 테스트 37개·E2E·`smoke:price-concurrency`가 통과했다.

## 3. 결과

### 로컬(같은 k6 스크립트, 쓰기 포함)

| 정점 처리량 | 변경 전 | 변경 후 |
| --- | --- | --- |
| 20 req/s | 실패 0% · p95 2.3초 · 쓰기 p95 5.8초 · 누락 18 | - |
| 40 req/s | **실패 81%** · p95 0.8~0.9초(실패 요청 포함이라 의미가 약함) · 누락 30 | **실패 0%** · p95 약 75~80ms · 누락 0 · 쓰기 p95 77ms |
| 60 req/s | - | 실패 79%(한계 초과) |
| 80 req/s | 실패 62% · p95 6초 | 실패 약 49% |

변경 전에는 20 req/s에서 이미 지연이 초 단위였고 40 req/s에서 무너졌다. 변경 후에는 40 req/s까지 지연이 두 자릿수 ms로 유지된다. 한계점은 40~60 req/s 사이다. 한 대의 노트북에서 k6·Worker·DB가 CPU를 나눠 쓰므로 이 수치를 서비스 처리량으로 해석하면 안 된다.

### 운영 읽기(한국, k6 2분, 12 VU, 약 54 req/s, 6,520건, 실패 0)

| 시나리오 | p50 | p95 |
| --- | --- | --- |
| 첫 화면(캐시 적중·stale) | 206ms | 271ms |
| 지도 z11, 캐시 우회(DB 경유, 2 VU) | 798ms | 915ms |
| 장소 상세(20곳, 대부분 엣지 캐시) | 155ms | 180ms |

### staging 쓰기·로그인(한국, 운영과 같은 경로, 순차 요청, 각 48회)

요청마다 새 visitor로 보내고, 운영과 같은 rate limit이 걸려 있어 8회씩 6라운드로 나눠 라운드 사이에 staging의 버킷을 비웠다(429·오류 0건). 같은 staging에 변경 전 코드(`056b806`)와 현재 코드를 각각 배포해 측정했고, 현재 코드는 시간대 차이를 확인하려고 두 번 쟀다.

| 요청 | 변경 전 p50 / p95 | 변경 후 p50 / p95 | 변경 후 재측정 p50 / p95 |
| --- | --- | --- | --- |
| 가격 제보 POST | 1,956ms / 2,064ms | 1,549ms / 1,677ms | 1,534ms / 1,655ms |
| 로그인 POST | 1,693ms / 1,816ms | 1,287ms / 1,385ms | 1,273ms / 1,394ms |

가격 제보는 약 21%(약 400ms), 로그인은 약 24%(약 400ms) 빨라졌다. 줄어든 시간이 두 요청에서 거의 같은 것은 연결 수립과 타입 조회 왕복처럼 요청 종류와 무관한 고정 비용이 빠졌기 때문으로 보인다. 변경 후에도 1.3~1.5초라 쓰기·로그인은 여전히 느리다(남은 구문 왕복과 Turnstile 검증 호출이 합쳐진 값이며, 구성 요소별로 나눠 재지는 않았다).

운영 읽기 경로는 변경 전과 **같다**(인앱 브라우저 재측정: z11 미스 p50 853ms 대 763ms는 변동 범위, 상세 540ms 대 554ms). 읽기는 원래 연결 1개 + 쿼리 1개였고 타입 조회 쿼리는 Hyperdrive가 캐시하고 있었기 때문이다. 효과는 구문과 연결이 여러 개인 쓰기·인증 경로에 있다.

## 4. 한계

- **운영 DB 쓰기는 여전히 측정하지 않았다.** 대신 같은 경로의 staging(분리된 DB)로 쟀다. staging은 DB 크기·같은 컨테이너의 다른 부하가 운영과 같다고 보장할 수 없고, 순차 요청이라 부하 상황의 쓰기 처리량은 모른다.
- 로컬 수치는 한 대에서 세 프로세스가 CPU를 나눈 값이고 운영 Hyperdrive의 연결 풀링이 없다. 운영 한계 처리량은 모른다.
- 한계를 넘기면 부하를 덜어내지 않고 연결 거부·503으로 무너진다(로컬 dev 서버 기준). 운영에서는 Cloudflare가 앞단에서 흡수하지만 검증하지 않았다.
- 부하 상황의 rate limit 정확도(고정 윈도우 경계 burst)와 장시간 soak 테스트는 하지 않았다.

## 5. 시행착오

- 닫힌 VU 루프 + 실패 시 무휴식: `connection refused`로 요청의 98%가 즉시 실패. 서킷 브레이커가 DB를 막은 것으로 먼저 의심했지만 오류 문자열(`dial: connection refused`)이 부하 모델 문제임을 보여 줬다.
- 지도 SQL을 리터럴·단순 프로토콜로 보내는 시도는 이득이 없어 되돌렸다([한국 측정](2026-11-24-한국-측정.md) §3).
