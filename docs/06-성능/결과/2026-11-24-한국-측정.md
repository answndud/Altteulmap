# 2026-11-24 운영 지연 측정과 개선

운영 DB를 VPS(오스트리아)로 옮긴 뒤 처음 잰 실측과, 그 결과로 한 개선을 기록한다. 성능 수치의 원본은 이 문서이고 README·ADR은 여기로 링크한다.

## 환경

| 항목 | 값 |
| --- | --- |
| 측정 위치 | 한국 개발 머신(`cdn-cgi/trace` `loc=KR`). 이 Worker(`workers.dev`)는 ICN이 아니라 PDX 콜로로 들어간다 |
| 측정 도구 | Claude 인앱 브라우저에서 `fetch` 왕복 시간(`performance.now`), 응답의 `Server-Timing: db;dur` |
| 경로 | 브라우저 → Cloudflare(PDX) → Worker(smart placement) → Hyperdrive → Workers VPC → Tunnel → VPS Postgres 17 |
| 데이터 | 운영 DB: 활성 장소 1,000곳, 가격 제보 4,978건 |
| 목표 | 공개 조회 p95 1초 이하(서비스 자체 목표, SLO 아님) |

## 1. 문제: 먼 DB에서는 쿼리 개수가 비용이다

| 측정 | 값 |
| --- | --- |
| DB 없는 요청(`/api/config/public`) p50 / p95 | 160ms / 230ms |
| Worker 안 `select 1` | 14ms |
| 쿼리 1개 왕복(Worker ↔ VPS) | 약 0.35~0.4초 |
| 개선 전 장소 상세 p50 / p95 | 1,551ms / 1,632ms (쿼리 5개) |

- 가설 1: 상세의 쿼리 5개를 `Promise.all`로 병렬화하면 0.4초 수준이 된다. → **틀렸다.** 서브쿼리로 의존성을 없애 병렬로 보내도 1.6초 그대로였다. Hyperdrive 경유에서는 한 연결(`max: 1`)의 쿼리가 사실상 순차로 처리된다.
- 가설 2: 쿼리 *수*를 줄여야 한다. → 맞았다.

## 3. 시도했다가 버린 것

- **Worker를 `aws:eu-central-1`에 고정**: DB 왕복은 줄지만 호출자 ↔ Worker 구간이 늘어 지도 약 5.6초로 더 느려졌다. smart placement만 켰다.
- **상세 쿼리 병렬화**: 위 가설 1. 효과 없음.
- **Worker를 EU 리전에 다시 고정(단일 쿼리 구조에서 재시도)**: DB 구간은 525 → 93ms로 줄지만 전체는 763 → 797ms, DB 없는 요청은 189 → 320ms로 나빠졌다. 큰 응답이 Frankfurt에서 방문자까지 가는 구간이 길어진다.
- **파라미터를 SQL 리터럴로 넣어 단순 프로토콜로 전송**: 같은 결과를 돌려주지만 지도 DB 구간은 525 → 582ms로 이득이 없었다. 작은 결과에서는 왕복이 2번 → 1번(345 → 180ms)으로 줄지만, 지도는 결과가 약 140KB라 전송량이 지배적이다(+140KB당 약 +130ms).
- **`prepare: true`**: Hyperdrive 쿼리 캐시는 파라미터 없는 쿼리와 준비된 쿼리에서 적중하지만, 앱이 쓰는 drizzle은 `unsafe()`로 실행해 이 옵션이 적용되지 않아 변화가 없었다. 캐시를 쓰면 세션 조회 같은 즉시 반영이 필요한 읽기도 캐시될 수 있어 켜지 않았다.

- **응답 필드 축소(`description`·`note` 제외)**: 항목당 약 110B(전체의 약 20%)라 DB 전송량이 약 20KB 줄 뿐이고(약 20ms), 상세 시트가 목록 항목에서 이 필드를 바로 읽어 쓴다. 이득에 비해 화면이 깨질 위험이 커서 하지 않았다.

## 4. stale-while-revalidate (2026-11-24)

미스 자체를 줄이기 어렵다는 결론(§3)에 따라, 사용자가 미스를 겪는 빈도를 줄였다. 익명 viewport 응답을 엣지 캐시에 **60초 신선 + 180초 stale**로 저장한다. 신선 기간이 지나면 첫 요청은 저장된 응답을 즉시 받고, `waitUntil`로 백그라운드에서 새로 만들어 캐시를 채운다(같은 URL의 갱신은 isolate당 1개). 응답 헤더 `X-Altteulmap-Map-Cache`가 `edge-hit`/`edge-stale`/`miss`를 알려 준다.

한국 머신에서 같은 첫 화면 URL을 6초 간격으로 36회(약 3.6분) 요청한 결과(`curl` 전체 시간, 연결·TLS 약 0.35초 포함):

| 상태 | 횟수 | p50 / p95 |
| --- | --- | --- |
| edge-hit | 28 | 590ms / 748ms |
| edge-stale | 6 | 590ms / 736ms |
| miss | 2 | 1,231ms / 1,413ms |

`edge-stale`이 `edge-hit`과 같은 지연으로 응답했다. SWR이 없었다면 stale 6회가 전부 미스였을 것이므로 미스 비율은 약 22%(8/36)에서 5.6%(2/36)로 줄었다. 남은 미스 2회는 PDX·SEA 콜로의 첫 요청이다(한국 트래픽이 PDX·SEA·DFW로 나뉘어 들어오고 콜로마다 캐시가 따로다). `tests/integration/map-edge-cache.test.ts`가 신선·stale·만료·중복 갱신 방지·실행 컨텍스트 없음을 가짜 캐시로 검증한다.

## 5. 남은 병목

- 진짜 캐시 미스(콜로의 첫 요청, 4분 넘게 조용한 뒤)는 zoom 11 p95가 약 1~1.2초로 목표(1초)에 걸친다. SQL 자체는 VPS에서 계획+실행 약 11ms라 남은 시간은 연결(약 0.17초)과 쿼리 왕복, 결과 약 140KB 전송이다. 코드로는 더 줄이지 못했고(§3), 남은 방법은 목록 건수(100) 축소나 가까운 리전 Postgres로 Hyperdrive 대상을 바꾸는 것이다.
- 표본이 작다(n=14~30). 부하 상황 처리량(k6)은 측정하지 않았다.
- 캐시 때문에 가격 승인 반영이 늦을 수 있다. 보통 60~120초이고, 트래픽이 없던 뒤 첫 요청은 최대 약 4분(60초 신선 + 180초 stale) 전 데이터를 볼 수 있다.
