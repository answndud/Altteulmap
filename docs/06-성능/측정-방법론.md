# 성능 측정 방법론

## 측정 단위

- workload: 지도 bbox, category filter, global query, 상세 조회
- fixture: local disposable PostgreSQL seed와 production read-only smoke의 환경을 구분
- warm-up: 첫 요청과 warm cache를 섞지 않도록 시나리오에서 명시
- 지표: p50/p95/p99, error rate, 응답 크기, DB query duration, connection/timeout
- 결과: commit, 실행일, Node/DB/runtime, fixture 규모, 원본 output을 함께 보존

## 성공 기준

현재 운영 SLO로 확정된 수치는 없다. 기존 문서의 300ms 지도 p95와 Hyperdrive trigger는 판단 기준이며, 실제 기준으로 승격하기 전에 트래픽 규모와 error budget을 정한다.

## 재현 명령

- npm run map:measure
- npm run perf:client
- MAP_MEASURE_URL=https://altteulmap.altteul-lab.workers.dev npm run map:measure

원격 명령은 read-only 환경과 허용된 공개 URL에 한정한다. 쓰기 smoke와 admin QA를 성능 측정에 섞지 않는다.

## 결과 해석 규칙

- iterations 기본값은 12, warmups 기본값은 2, timeout 기본값은 10초다. 이는 scripts/measure-map-api.mjs의 현재 기본값이다.
- p95는 ceil 기반 percentile이며 작은 샘플에서는 한 번의 느린 요청에 크게 영향을 받는다.
- script는 response source가 database이고 mock=false인지 확인하며, returnedCount가 2,000을 넘으면 실패한다.
- 측정 대상에는 seoul-viewport-z11, seoul-category-food-z13, global-query-kimbap, wide-bbox-cap 네 시나리오가 있다.
- 결과가 좋더라도 DB query plan, connection churn, error rate가 없으면 “성능이 보장된다”고 결론내리지 않는다.

## 변경 전후 비교 표준

동일 commit 기준으로 before/after를 비교하려면 같은 fixture, 같은 URL, 같은 iterations/warmups, 같은 region/runtime에서 각각 원본 JSON을 보존한다. 평균만 비교하지 말고 p50/p95/p99, count/returnedCount, error rate를 함께 본다. 현재 저장소에는 일부 historical p95만 있어 개선률 계산을 하지 않는다.
